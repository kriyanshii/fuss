## how-it-works.md

- **Each new LTX file gets the next TXID after the previous file, and this holds across kills and restarts.** (process-kill, high)
  - Quote: > Litestream assigns each of these files the next monotonically incrementing _transaction ID_ (TXID) and stores checksums alongside the pages to ensure consistency.
  - Inject: SIGKILL Litestream in the middle of a sync or upload while writes keep flowing. Repeat at random intervals.
  - Observe: List the L0 directory under the replica's ltx/ prefix after each restart. Parse the min/max TXIDs from the file names. Every new file's min_txid must equal the previous max_txid+1. No TXID may be reused or go backwards. No file may have the same range as an earlier file but different content.
  - Workload: Start litestream replicate. Loop: INSERT INTO t(seq) VALUES(n), one row per transaction. Every 1–5 s, kill -9 and restart Litestream. Snapshot the replica's file listing before and after each restart.
  - Guess: Guess: if the kill lands after a file is staged locally but before it is uploaded, a restart might recompute the next TXID from the replica and reuse that TXID for different pages.
- **Restore either produces an intact database or refuses. It never silently produces a corrupted database when the chain has a gap.** (process-kill, high)
  - Quote: > Because TXIDs form a contiguous sequence, Litestream can verify that no transactions are missing before restoring—any gap in the sequence would otherwise result in a corrupted database file.
  - Inject: Kill repeatedly during uploads and compactions, then run restore while Litestream is down and again while it is running.
  - Observe: For each restore: either it exits non-zero, or the output passes PRAGMA integrity_check and its rows are a consistent prefix of Fuss's recorded commit history. Consistent prefix means seq values 1..k with no holes, and k falls on a transaction boundary.
  - Workload: Use multi-row transactions that are tagged with a txn id and a row count. Kill and restart Litestream in a loop. Periodically run litestream restore -o /tmp/rN.db <db>, then integrity_check and the prefix check.
  - Guess: Guess: a kill during compaction might leave an overlapping or partial higher-level file that the gap check treats as covering the range, even though it does not.
- **When the database is idle, no new LTX files or TXIDs appear.** (restart, medium)
  - Quote: > An incremental sync that finds no newly committed WAL pages writes no file and assigns no TXID.
  - Inject: Stop all writes, restart Litestream once, then wait several sync intervals.
  - Observe: After any full-state file written at startup, the replica's L0 listing and highest TXID stay unchanged for the rest of the idle period.
  - Workload: Insert 100 rows. Wait for replication. Stop writing. Restart Litestream. Record the L0 listing every second for 60 s.
  - Guess: Guess: Litestream's own checkpoints, or a WAL header change after a restart, might be treated as new pages and produce empty-change files every interval.
- **If the WAL was changed behind Litestream's back while it was down, the next sync writes a full-state file, and restores still include every committed write.** (restart, high)
  - Quote: > A sync that has to establish or repair replication state writes a full-state file instead, even when there are no new pages.
  - Inject: Kill Litestream. While it is down, commit writes and run PRAGMA wal_checkpoint(TRUNCATE) from Fuss's client. Then restart Litestream.
  - Observe: After restart, a new LTX file appears whose TXID continues the sequence. A restore taken after it appears contains every row committed while Litestream was down and passes integrity_check.
  - Workload: Insert rows 1..N under Litestream. Kill it. Insert rows N+1..M. Run wal_checkpoint(TRUNCATE). Restart Litestream. Wait one sync interval. Restore and check that rows 1..M are present.
  - Guess: Guess: if the WAL was truncated and then rewritten with a similar-looking header, Litestream might not detect the discontinuity. It would then ship only the new WAL pages and lose the checkpointed changes.
- **When a large catch-up is split into several LTX files, each split falls on a transaction boundary. A single huge transaction is never split.** (process-kill, high)
  - Quote: > It checks that limit only after reading a WAL commit marker, so a batch never ends mid-transaction. A single transaction larger than the limit still goes into one file.
  - Inject: Keep Litestream down while a large backlog accumulates, or kill it partway through catch-up uploads. Then restart.
  - Observe: For every L0 max_txid, restore -txid <that txid> produces a database whose tagged transactions are all complete. No transaction has only some of its rows present. The single oversized transaction appears in exactly one L0 file.
  - Workload: Set max-sync-wal-bytes to 1MB. Kill Litestream. Commit many 300KB transactions plus one 5MB transaction, each with a txn id and row count. Restart. Restore at each L0 boundary and check that every transaction is all-or-nothing.
  - Guess: Guess: a kill between two split files might lead the restarted process to resume at a WAL offset in the middle of a transaction.
- **File names accurately state the TXID range of the file's contents, including files written just before a crash.** (process-kill, medium)
  - Quote: > LTX files are named after the TXID range they cover—for example, `0000000000000001-0000000000000005.ltx` covers TXIDs 1 through 5.
  - Inject: During upload and during compaction.
  - Observe: For each file name, litestream ltx -level all reports matching min/max values. Restoring to each listed max_txid either succeeds with an integrity-clean prefix or fails cleanly. A name never covers content from a different range.
  - Workload: Run continuous writes with kill/restart cycles. After each cycle, cross-check the file names in the replica against the ltx command output and dry-run restore plans.
  - Guess: Guess: a compaction killed mid-write on a file replica might leave a correctly named file that is truncated or partial.
- **Files that were staged locally but not yet uploaded are still uploaded after a crash or disk-full recovery. Nothing committed is permanently skipped.** (disk-full, medium)
  - Quote: > LTX files are staged in a hidden directory next to your database (e.g. `/var/lib/.db-litestream` for a database at `/var/lib/db`) and then uploaded to the replica, where they are organized by compaction level under an `ltx/` prefix.
  - Inject: Fill the filesystem that holds the database and its .db-litestream directory while writes continue. Free the space later. Optionally kill Litestream while the disk is full.
  - Observe: After space is freed and Litestream runs, the replica TXID chain is contiguous. A restore contains every row that SQLite reported as committed. Rows whose commits failed with SQLITE_FULL are absent.
  - Workload: Put the database on a small loopback filesystem. Insert rows in a loop and record which commits succeeded. Fill the disk with a ballast file. Remove the ballast. Optionally restart Litestream. Wait, restore, and compare against the recorded commits.
  - Guess: Guess: a partially written staging file left by ENOSPC might later be uploaded as-is, or block later uploads.
- **While Litestream runs, other clients cannot restart the WAL under it, so replication stays complete even if an app forces checkpoints.** (concurrent-calls, medium)
  - Quote: > It starts a long-running read transaction to prevent any other process from checkpointing and restarting the WAL file.
  - Inject: While Litestream is running and writes are flowing, issue PRAGMA wal_checkpoint(TRUNCATE) and RESTART from a separate client.
  - Observe: The -wal file is not truncated to 0 while Litestream holds its read transaction; Fuss can watch the file size. Every committed row still appears in a later restore with a contiguous chain.
  - Workload: Thread A inserts rows continuously. Thread B calls wal_checkpoint(TRUNCATE) every 200 ms and logs the result and the WAL size. After 2 minutes, restore and check that all committed rows are present.
  - Guess: Guess: during Litestream's own checkpoint it must briefly release its read lock, and a racing external TRUNCATE checkpoint could slip in.
- **A restore applies changes in TXID order on top of the right snapshot, so the result reflects history in commit order.** (process-kill, high)
  - Quote: > To restore a database, Litestream fetches the most recent snapshot that does not overshoot the requested restore point and then applies each subsequent LTX file in TXID order to bring the database up to that point.
  - Inject: Kill during snapshot creation and during compaction. Then restore at several targets.
  - Observe: Restore at increasing -txid values gives monotonically growing prefixes of history. A row that was updated in sequence has the value of its last update before the target, never an earlier value after a later one. Dry-run output lists a snapshot whose max_txid is at or below the target, followed by contiguous files.
  - Workload: Run UPDATE kv SET v=v+1 WHERE k=1 alongside INSERTs. Set a short snapshot interval. Kill and restart. Restore at many TXIDs and check that kv.v and the row count never decrease as the target increases.
  - Guess: Guess: if a snapshot was interrupted and a partial snapshot file exists, the planner might choose it as the latest snapshot.
- **Restoring to exactly a file's max_txid includes that file.** (restart, high)
  - Quote: > A `-txid` target is inclusive: a file is eligible when its maximum TXID is less than or equal to the requested TXID.
  - Inject: After several restarts, so that files from both before and after the restarts exist.
  - Observe: restore -txid X, where X is an existing L0 max_txid, succeeds. Its contents strictly include the changes in the file ending at X, compared with restore at the previous boundary.
  - Workload: Insert rows with restarts in between. For each L0 file, restore at its max_txid and at the previous max_txid, and diff the results.
  - Guess: Guess: an off-by-one at the full-state file written on restart might exclude it.
- **Timestamp restores include only files created strictly before the target time, and the result stays a consistent prefix even if the clock jumped.** (clock-skew, medium)
  - Quote: > A `-timestamp` target is exclusive: a file is eligible only when it was created strictly before the requested timestamp, so a file whose creation time exactly equals the timestamp is skipped.
  - Inject: Step the system clock backward by minutes while writes continue, then forward again.
  - Observe: From the ltx listing's created times: restore -timestamp equal to a file's created time excludes that file. When created times are non-monotonic because of skew, a restore either fails or returns an integrity-clean, contiguous prefix. It never returns a database that skips a middle file.
  - Workload: Insert continuously. Set the clock back 10 min, keep inserting, then restore the clock. List files. Restore at each created timestamp and at points within the skewed window. Check the prefix property.
  - Guess: Guess: with backward skew, a later TXID can have an earlier timestamp. Filtering by time could select a non-contiguous set, or one whose gap check passes only by accident.
- **A restore to a TXID inside a file fails cleanly instead of partially applying that file.** (restart, high)
  - Quote: > Litestream replays whole LTX files and never applies part of one, so your restore points are the boundaries of the files that still exist in the replica. If skipping it leaves the plan short of the requested TXID, the restore fails with `no matching backup files available` even though the transaction itself was replicated.
  - Inject: After L0 files have expired and only multi-TXID L1 files cover a range, including across restarts.
  - Observe: restore -txid T, where T lies strictly inside an L1 range with no matching L0 boundary, exits with 'no matching backup files available' and leaves no output database, or none that is used. It never produces a database at a different TXID.
  - Workload: Set l0-retention to 10s and an L1 interval of 30s. Write bursts and restart once. Wait. Pick T inside an L1 file range. Restore -txid T -o /tmp/x.db and check the exit code and whether /tmp/x.db exists.
  - Guess: Guess: the planner might fall back to the nearest lower boundary and succeed silently, giving a database that differs from the requested point.
- **An L0 file is deleted only after both conditions hold: an L1 file covers it, and its age exceeds l0-retention. At every moment, the latest state stays restorable.** (clock-skew, medium)
  - Quote: > L0 files are removed once they have been compacted into L1 _and_ have outlived [`l0-retention`](/reference/config#l0-retention) (default `5m`), so a restore point that was available a few minutes ago can become permanently unreachable.
  - Inject: Jump the clock forward past l0-retention, combined with killing Litestream just before an L1 compaction finishes.
  - Observe: Poll the replica listing. Every deleted L0 range was already covered by an L1 file at deletion time. Restoring the latest TXID succeeds at every poll.
  - Workload: Set l0-retention to 1m. Write continuously. Repeatedly kill Litestream right after L0 uploads and before the L1 interval elapses. Set the clock forward 2h and restart. Poll the listing and restore the latest TXID.
  - Guess: Guess: a forward clock jump makes every L0 file look expired, and if L1 coverage is checked from stale in-memory state, uncovered L0 files might be deleted.
- **L2 compaction, even when interrupted, does not remove L1 files or break restores at L1 boundaries.** (process-kill, medium)
  - Quote: > Compacting L1 into L2 writes the larger file but leaves the source files in place, so L1 boundaries stay restorable until retention removes them.
  - Inject: During L2 compaction, which runs on a configurable short interval.
  - Observe: The set of L1 files never shrinks except through snapshot-retention pruning. Restoring at each previously seen L1 max_txid keeps succeeding.
  - Workload: Set short L1 and L2 intervals and a long snapshot retention. Write continuously and kill around L2 ticks. Record L1 listings and re-restore old L1 boundaries.
  - Guess: Guess: on restart, cleanup of leftovers from an interrupted compaction might remove source L1 files.
- **Retention never deletes the last snapshot, and never deletes files needed to replay forward from the oldest kept snapshot, even under clock jumps.** (clock-skew, high)
  - Quote: > This periodically runs and removes any snapshots older than the retention period as well as any LTX files older than the oldest snapshot. By default, the retention period is 24 hours. Litestream will always ensure there is at least one snapshot retained.
  - Inject: Jump the clock forward far beyond the retention period, possibly together with a kill during retention enforcement.
  - Observe: The snapshot level always has at least one file. Restoring the latest TXID always succeeds and contains all committed rows. No LTX file at or above the oldest snapshot's TXID disappears.
  - Workload: Set snapshot.interval to 1m and retention to 2m. Write continuously. Set the clock forward 30 days and restart. Poll the listing for snapshot count and restore the latest.
  - Guess: Guess: a forward jump ages every snapshot past the cutoff, and if the new snapshot is written after pruning, or its upload is killed, zero snapshots remain.
- **After retention runs, L1–L3 are all pruned at the same TXID cutoff.** (process-kill, low)
  - Quote: > **At the snapshot cutoff**, retention enforcement derives a single minimum snapshot TXID from `snapshot.retention` and applies that same cutoff to every configured compaction level in one pass, skipping L0, which has its own `l0-retention` schedule. L1, L2, and L3 do not age out independently by level; older history is pruned across all of them together.
  - Inject: During a retention enforcement pass.
  - Observe: After each pass, possibly interrupted, the lowest surviving min_txid across L1, L2, and L3 is consistent with one cutoff. Restore from the oldest snapshot to the latest TXID still succeeds.
  - Workload: Use short snapshot intervals and retention. Write continuously. Kill at random during retention windows. Compare the minimum TXID per level after each pass, and restore from the oldest snapshot.
  - Guess: Guess: the 'one pass' is not atomic on storage, so a kill mid-pass leaves levels pruned at different cutoffs. That is fine only if no chain is broken.
- **Compactions and snapshots keep happening on schedule even when Litestream restarts more often than the interval.** (restart, medium)
  - Quote: > - **L1, L2, L3** — compacted files, merged every 30 seconds, 5 minutes, and 1 hour by default. - **Snapshot level** — a full copy of the database, created every 24 hours by default.
  - Inject: Restart Litestream at a period shorter than the configured compaction or snapshot interval.
  - Observe: New L1, L2, and snapshot files still appear within roughly the configured interval of wall-clock time, rather than never appearing.
  - Workload: Set L1 to 30s and snapshot.interval to 2m. Write continuously. Restart every 20s for 10 min. Count new files per level.
  - Guess: Guess: interval timers may reset at process start, so frequent restarts starve compaction and snapshots, and restore time grows without bound.

## reference-replicate.md

- **While the daemon runs, committed SQLite writes keep reaching the replica, and a restarted daemon resumes this so that a restore returns a consistent prefix of committed writes.** (process-kill, medium)
  - Quote: > The `replicate` command starts a server to monitor & continuously replicate SQLite databases. This is the Litestream daemon itself—the long-running process you launch directly or via your service manager.
  - Inject: SIGKILL the daemon at random moments during a steady stream of commits, including mid-sync. Restart it with the same config, then repeat several times.
  - Observe: After a final quiet period, run `litestream restore` into a fresh path. Compare the restored rows against Fuss's own commit log. Every restored row must have been committed, the restored ids must form a gap-free prefix of the commit order, and `PRAGMA integrity_check` must return ok. After the last restart and a settle period, writes committed after that restart should also appear.
  - Workload: Configure a file:// replica. Start `litestream replicate -config c.yml`. A client loop runs `INSERT INTO t(id, v)` with monotonically increasing ids, one transaction each, and logs each commit acknowledgement to the Fuss history file. Kill -9 the daemon at random intervals and restart it. Stop the writes, wait, then restore and diff.
  - Guess: Guess: if the daemon is killed after copying part of the WAL but before recording its position, the restarted daemon could skip or duplicate a segment. The result would be a gap or a corrupt restore.
- **When the child process started with -exec exits for any reason, the Litestream process also exits.** (process-kill, high)
  - Quote: > -exec CMD
    Executes a subcommand. Litestream will exit when the child
    process exits. Useful for simple process management.
  - Inject: SIGKILL the child process, or let it exit on its own with a non-zero code, while Litestream is mid-replication and writes are in flight.
  - Observe: Check whether the litestream PID terminates within a bounded time after the child dies. Record the exit status. Then restore and check that the replica is a consistent, integrity-checked prefix of the writes the child committed.
  - Workload: `litestream replicate -exec "fuss-writer" -config c.yml`, where fuss-writer inserts rows in a loop and logs commits. Fuss kills fuss-writer with -9 at a random time, waits for litestream to exit, then runs restore and diffs.
  - Guess: Guess: if the child is killed by a signal rather than exiting cleanly, Litestream might not notice. It could hang, or it could exit before flushing the last sync and leave the replica further behind than expected.
- **A successful `replicate -once` run copies everything committed before it started to the replica, then exits.** (process-kill, high)
  - Quote: > The `-once` flag performs a single sync of all databases and their replicas, then exits instead of running as a continuous server.
  - Inject: Kill -9 some `-once` runs part-way through. Let a later `-once` run finish, then check.
  - Observe: After a `-once` run exits with code 0, restore the replica. It must contain every row Fuss logged as committed before that run started, and it must pass integrity_check. A killed run followed by a successful rerun must give the same guarantee. Repeated successful runs with no new writes must not change the restored contents.
  - Workload: Commit N rows and log them. Run `litestream replicate -once DB file:///replica`, killing it at a random delay. Rerun until it exits with code 0. Restore and diff against the log. Commit more rows and repeat. Finally, run -once twice with no writes in between and compare the two restores.
  - Guess: Guess: a run killed mid-upload could leave a partial WAL segment or snapshot file in the replica. The next run might trust that file, or restore might pick it up, giving a truncated or corrupt result.
- **Running `-once -force-snapshot` produces a new complete snapshot of each database in the replica.** (disk-full, medium)
  - Quote: > -force-snapshot—Forces a new snapshot to be taken for all databases. Useful for creating a complete backup before maintenance or when migrating databases between hosts.
  - Inject: Fill the replica filesystem part-way through writing the snapshot. Separately, kill -9 the process mid-snapshot.
  - Observe: On a successful exit, a new snapshot file appears in the replica directory, and restore returns all rows committed before the run. On a failure, the exit code is non-zero, and restore still returns a consistent earlier state rather than a corrupt or partial database.
  - Workload: Replicate normally for a while, then stop. Commit more rows. Run `litestream replicate -once -force-snapshot -config c.yml` with the replica directory on a small tmpfs, filling it with junk at a random point. Free the space, list the replica files, restore, and diff.
  - Guess: Guess: a snapshot file written in place, rather than written to a temp file and renamed, could be left truncated after ENOSPC or a kill, and restore might choose it as the latest snapshot.
- **Running `-once -enforce-retention` deletes only the snapshots older than the configured retention period, and the replica stays restorable.** (clock-skew, medium)
  - Quote: > -enforce-retention—Applies the configured snapshot retention policy, removing snapshots older than the retention period.
  - Inject: Run the retention pass with the system clock skewed forward or backward relative to when the snapshots were made. Separately, kill -9 the process mid-deletion.
  - Observe: Using Fuss's own record of when each snapshot was forced, check that only snapshots older than the retention period disappear from the replica directory. Check that restore still returns the latest committed data and passes integrity_check, including after a killed retention run.
  - Workload: In the config, set a short retention, e.g. 1h. Create several snapshots via `-once -force-snapshot`, interleaved with inserts, and log the times. Skew the clock with faketime or a namespace clock. Run `litestream replicate -once -enforce-retention -config c.yml`. List the replica files, restore, and diff.
  - Guess: Guess: if retention compares snapshot timestamps against the local wall clock, a forward skew could delete every snapshot, including the only one needed to restore. A kill mid-deletion could also orphan WAL segments.
- **If the database file is missing at startup, the daemon restores it from the replica before replicating. If the file exists, it is not overwritten.** (process-kill, high)
  - Quote: > The `-restore-if-db-not-exists` flag restores the database from its replica before replication starts if the local database file is missing.
  - Inject: Kill -9 the daemon while it is still restoring the missing database, then start it again with the same flag.
  - Observe: After the restart settles, the local database must pass integrity_check and contain a consistent prefix that includes all rows Fuss confirmed were replicated before the delete. The test fails if a partially restored file from the killed run is treated as existing and then replicated, shrinking or corrupting the replica. In a separate run, start with an existing local database that differs from the replica, and confirm its contents are left untouched.
  - Workload: Replicate N rows and confirm them by restoring to a scratch path. Stop the daemon, then delete the db, -wal, and -shm files. Start `litestream replicate -restore-if-db-not-exists -config c.yml` and kill it at a random early delay. Restart it, wait, read the db, and diff. Then add rows and restore again to check that replication continues correctly.
  - Guess: Guess: if the restore writes directly to DB_PATH instead of a temp file that is renamed at the end, a killed restore leaves a partial file. The next start sees the file as existing, skips the restore, and begins replicating the damaged database.
- **With `-restore-if-db-not-exists` and an empty replica, the daemon does not fail. It starts replicating the database.** (restart, medium)
  - Quote: > On first start with no existing backup, replication proceeds normally.
  - Inject: Start against an empty replica destination. Restart the daemon shortly after the first writes, before any snapshot may exist.
  - Observe: The daemon keeps running without exiting with an error. After writes and a restart, restore returns the committed rows with no gaps.
  - Workload: Use an empty file:// replica directory and no database file. Start `litestream replicate -restore-if-db-not-exists -config c.yml`. The client creates the database and inserts rows. Kill and restart the daemon, wait, then restore and diff.
  - Guess: Guess: a restart that happens after the database exists but before the first snapshot lands might try to restore from an incomplete replica and error out, or overwrite the new local database.

## reference-restore.md

- **Without -force, restore never modifies a database file that already exists at the output path.** (concurrent-calls, high)
  - Quote: > Restoration will only run if the output database file does not exist so you cannot accidentally overwrite your running database.
  - Inject: While a client is actively writing to the live database and `litestream replicate` is running, launch `litestream restore` targeting that same live path.
  - Observe: Restore exits non-zero. The live DB file is never modified by restore: SQLite reads stay consistent and every row in Fuss's history is still present with the right value. The mtime only moves for Fuss's own writes.
  - Workload: Create table t(seq INTEGER PRIMARY KEY, v). Start replicate. Loop: insert seq=n and log n after commit. Mid-loop, run `litestream restore -config cfg /data/app.db` repeatedly. Stop. Compare DB rows to the log.
  - Guess: Guess: the existence check and the open/create of the output may not be one atomic step. A file created or truncated between them could be clobbered.
- **Restore without -force refuses when the output file is non-empty or when any -wal/-shm/-journal sidecar exists, including leftovers from a crashed earlier restore.** (process-kill, high)
  - Quote: > If the output path already exists and is not empty (or if SQLite sidecar files like `-wal`, `-shm`, or `-journal` exist), the restore will fail with an error:
  - Inject: SIGKILL a first `restore -o X` part-way through, after the output file has been created but before exit. Then rerun the same restore without -force.
  - Observe: If the killed run left a non-empty X or any X-wal/X-shm/X-journal, the second run must exit non-zero with 'cannot restore, output path already exists and is not empty'. It must not exit 0 and leave a half-built file looking like a finished restore.
  - Workload: Build a large replica (many inserts, wait for sync). Run `restore -o /tmp/r.db URL` and kill -9 at random delays. List /tmp/r.db*. Rerun `restore -o /tmp/r.db URL` and record the exit code and stderr.
  - Guess: Guess: the crashed restore may leave only a sidecar or a temp file with a different name. The check might then pass on an empty main file that is not really clean.
- **The 'output exists' check is done before planning, so a reused path always gives the overwrite error, even when the -txid is invalid.** (other, high)
  - Quote: > Litestream refuses to write over an existing non-empty file, and that check runs before the restore plan is evaluated, so reusing one path reports `cannot restore, output path already exists and is not empty` instead of the granularity error above.
  - Inject: After a successful restore to path P, rerun restore to P with a -txid known to be unreachable (not any file's max_txid).
  - Observe: stderr contains the 'already exists and is not empty' message and not 'no matching backup files available'. Exit is non-zero and P is unchanged (same hash).
  - Workload: Insert rows and wait for sync. Run `restore -o P URL`. Read `litestream ltx -level all` to pick a non-boundary TXID T. Run `restore -txid T -o P URL` and check the message.
  - Guess: Guess: when -txid is given, a code path may resolve the plan first for validation and report the plan error.
- **Point-in-time restore applies whole LTX files only, so the result is always exactly the state at some file boundary at or below the target, never a partial mix.** (process-kill, high)
  - Quote: > A file whose range would overshoot the target is skipped entirely rather than partially applied, so not every replicated transaction is a valid restore point.
  - Inject: SIGKILL `litestream replicate` at random moments during a write burst, restart it, then restore to several -txid values.
  - Observe: Each restored DB holds a contiguous prefix of Fuss's logged writes (seq 1..k with no gaps). k matches exactly the writes up to the max_txid of some listed LTX file at or below the target. No row from beyond the target appears.
  - Workload: One insert per transaction, logged after commit. Kill and restart replicate several times. For each max_txid M in `ltx -level all`, run `restore -txid M -o /tmp/rM.db`. Check prefix-closure and monotonicity of k as M grows.
  - Guess: Guess: an LTX file written while replicate was being killed might be applied partially or include an uncommitted page, breaking prefix-closure.
- **Restoring with -txid equal to a file's max_txid includes that file, and nothing with a higher max_txid is applied.** (restart, high)
  - Quote: > `-txid` is inclusive: a file is eligible when its maximum TXID is at or below the requested TXID.
  - Inject: Restart replicate between bursts so L0 and L1 boundaries differ, then restore to a boundary value and to boundary minus one.
  - Observe: With `restore -json`, the reported txid equals the requested boundary M. Restoring with M-1 (when it is not a boundary) yields an older state or 'no matching backup files available', never M's rows.
  - Workload: Insert N rows in bursts, restarting replicate in between. Read the ltx listing. For each boundary M, run `restore -json -txid M` and `restore -txid M-1`. Compare row counts against the log.
  - Guess: Guess: an off-by-one in the comparison, or confusion between L0 and L1 file sets after restart.
- **A timestamp restore uses only files whose created time is strictly earlier than the requested time.** (clock-skew, medium)
  - Quote: > `-timestamp` is exclusive: a file must have been created strictly before the requested timestamp, so a file created at exactly that instant is skipped.
  - Inject: Step the wall clock of the replicate process backward and forward between write bursts, so LTX created times are non-monotonic relative to TXID order.

- **A plain restore returns the latest replicated state, which includes every write covered by the highest listed max_txid.** (process-kill, high)

  - Observe: Exit is non-zero and there is no 'no matching backups found' log line. Separately, an empty replica gives exit 0 and the log message.

- **Running the idempotent restore repeatedly gives exit 0 and never overwrites an existing database.** (restart, high)

- Database exists: exits successfully without overwriting
- Database doesn't exist, backups available: restores the database

  - Inject: Rerun the idempotent restore many times, including right after a SIGKILLed earlier attempt.

  - Guess: Guess: restore may write the final path in place rather than via temp-and-rename. A crash then leaves a partial DB that -if-db-not-exists accepts as existing forever.

  - Inject: Run out of space on the output filesystem near the end of the restore.
  - Observe: Every exit-0 run produces a DB that passes Fuss's own PRAGMA integrity_check and holds a log prefix. Any exit-0 run with a corrupt DB violates the promise.

- **With -json, stdout is always valid JSON (or empty), even when errors occur.** (disk-full, medium)
  - Quote: > All log messages are written to stderr so stdout remains parseable JSON.
  - Inject: Trigger failures (full disk, existing output, missing replica) while running with -json.
  - Observe: stdout parses as JSON or is empty. On success the txid field matches the restored content measured against the log.
  - Workload: Run `restore -json` under each failure mode plus success. Capture stdout separately and parse it. On success, compare txid to `ltx` max_txid.
  - Guess: Guess: some error paths may print plain-text messages to stdout.
- **The follow-mode -txid sidecar is never seen partially written, and it is only advanced after the batch it names is applied.** (process-kill, high)
  - Quote: > The `-txid` file is written atomically (using a temporary file, fsync, and rename) after each batch of LTX files is applied.
  - Inject: SIGKILL the `restore -f` process repeatedly at random moments while new LTX files keep arriving.
  - Observe: Every read of X-txid (polled continuously, and after each kill) is a complete, valid hex TXID that never decreases. The DB opened read-only contains at least all logged writes up to that TXID.
  - Workload: Primary writes with replicate running. Start `restore -f -follow-interval 200ms -o /tmp/f.db URL`. Poll /tmp/f.db-txid constantly. Kill -9 the follower at random and check the file contents and the DB-vs-txid relation.
  - Guess: Guess: the -txid file may be renamed before the DB pages are fsynced, so after a crash the sidecar claims more than the DB holds.
- **After a crash, restarting follow mode resumes and converges to the primary's latest state, with correct contents.** (process-kill, high)
  - Quote: > If the follow mode process crashes or is terminated unexpectedly, it can resume from the saved TXID on restart without requiring a full re-restore.
  - Inject: SIGKILL the follower mid-batch, keep writing on the primary, then restart the follower with the same arguments.
  - Observe: The restarted follower does not error. Once writes stop, it converges so the read-only DB equals the full log, passes integrity_check, and shows no duplicated or missing seq. Resuming should take much less time and download than a fresh restore.
  - Workload: Primary inserts continuously. Run `restore -f -o /tmp/f.db`, kill -9 it, wait, restart it. Repeat 20 times. Stop writes, wait several follow intervals, and diff against the log.
  - Guess: Guess: re-applying a batch partly applied before the crash may not be idempotent, leaving page-level corruption.
- **On restart, follow mode starts from the saved TXID rather than redoing history.** (restart, medium)
  - Quote: > When follow mode starts and detects both an existing database file and its corresponding `-txid` file, it reads the saved TXID and resumes replication from that point.
  - Inject: Cleanly SIGINT the follower, then restart it after the primary has advanced.
  - Observe: The resumed follower's DB moves forward from the saved TXID and ends equal to the log. Logs, timing, or `-json` show no full restore. The DB is not replaced wholesale: the inode is unchanged.
  - Workload: Primary inserts. Follower `-f` runs, SIGINT it, record the inode and the -txid value. Insert more rows. Restart the follower and confirm convergence and the same inode.
  - Guess: Guess: if retention compacted the range just after the saved TXID into an L1 file, resume might mis-select files or start over.
- **SIGINT stops follow mode leaving a consistent DB and a matching -txid file.** (process-kill, high)
  - Quote: > Follow mode runs indefinitely until stopped with `Ctrl+C` (SIGINT), at which point it shuts down cleanly.
  - Inject: Send SIGINT during an active batch apply.
  - Observe: The process exits promptly. The DB passes integrity_check, the -txid file is valid and matches the DB contents per the log, and no -wal or temp sidecar is left behind.
  - Workload: Heavy primary writes. Follower with `-follow-interval 100ms`. Send SIGINT at random times. Check the DB, sidecar, and leftovers.
  - Guess: Guess: signal handling may cancel mid-batch without updating or rolling back state consistently.
- **If a crash leaves a DB without a -txid file, restarting follow mode errors instead of guessing.** (process-kill, medium)
  - Quote: > If the database file exists but the `-txid` file is missing, follow mode cannot determine where to resume safely and will return an error.
  - Inject: SIGKILL the follower during the initial restore, after the DB file appears but before the first -txid file is written.
  - Observe: Whenever the post-kill state is DB present and -txid absent, the restarted `restore -f` exits non-zero. It must not run on silently.
  - Workload: Large replica. Start `restore -f -o /tmp/f.db` and poll for /tmp/f.db. Kill -9 as soon as it exists. If no f.db-txid exists, restart and record the exit code.
  - Guess: Guess: the existence check may instead hit the generic 'output exists' guard, or treat the file as resumable from zero.
- **A follower restarted after retention pruned its resume point exits with an error rather than hanging.** (restart, medium)
  - Quote: > If the saved TXID is behind the earliest available snapshot (because retention policies have pruned older data), follow mode returns a clear error instead of silently stalling.
  - Inject: Stop the follower, let replicate (configured with very short retention) prune past the saved TXID, then restart the follower.
  - Observe: The follower exits non-zero within a bounded time. It is a failure if it stays running with the -txid frozen and the DB never advancing.
  - Workload: Config with short retention and snapshot interval. Primary writes. Follower runs, then SIGINT it. Keep writing until the ltx listing's earliest snapshot exceeds the saved TXID. Restart the follower with a timeout.

  - Quote: > | Saved TXID is ahead of latest snapshot | Error: delete the database and `-txid` file to re-restore |
  - Inject: After the follower has a high saved TXID, restart it against a different, younger replica URL with the same output path.
  - Observe: The follower exits non-zero, and the DB and -txid file are unchanged (same hashes).
  - Workload: Replica A has many writes and the follower syncs from it, then SIGINT it. Create a fresh DB B with a few writes replicated to path B. Run `restore -f -o same.db B-URL`.
  - Guess: Guess: the check may compare only against snapshots and miss L0-only replicas, applying B's pages over A's DB.

  - Quote: > Determines the number of WAL files downloaded in parallel.

  - Observe: Both restored DBs have identical logical contents (a row-by-row dump) and the same -json txid.

## tips.md

- **Litestream's checkpoint write locks are short enough that an application using busy_timeout=5000 should never see SQLITE_BUSY caused by Litestream.** (concurrent-calls, high)
  - Quote: > However, Litestream requires periodic but short write locks on the database when checkpointing occurs. SQLite will return an error by default if your application tries to obtain a write lock at the same time. To prevent this, your application will need to set the [`busy_timeout`
][busy_timeout] pragma when it initializes the database connection. This pragma
will wait up to a given number of milliseconds before failing a query if it is
blocked on a write. It is recommended to set this to 5 seconds:
  - Inject: Continuously, with the most pressure around checkpoints. Grow the WAL past its truncate or checkpoint thresholds so Litestream checkpoints often. Optionally add disk-full or slow-disk pressure on the replica side during those checkpoints.
  - Observe: Fuss records in its history file every SQLITE_BUSY or SQLITE_LOCKED error and the latency of each write transaction. The promise holds if no write fails with BUSY and no write blocks close to 5s while only Fuss's writer and Litestream touch the database.
  - Workload: 1) Create db and open a connection with PRAGMA busy_timeout=5000. 2) Start `litestream replicate -config fuss.yml` with a file replica. 3) Loop many small INSERTs with a monotonically increasing id plus a few large blobs to force WAL growth and checkpoints, for several minutes. 4) Log each commit's outcome and duration. 5) Stop Litestream with SIGTERM.
  - Guess: Guess: when the replica is slow or the disk is full, a checkpoint might hold the write lock while it waits on I/O, so a lock that should be short could exceed 5s.
- **If the database is in a non-WAL journal mode, Litestream switches it to WAL when it starts replicating.** (restart, high)
  - Quote: > Litestream will automatically set the database mode to `WAL` if it has not already been enabled by the application.
  - Inject: Start Litestream on a database left in rollback (DELETE) journal mode. Also kill it with SIGKILL immediately after startup, at varying delays, then restart it.
  - Observe: Fuss runs `PRAGMA journal_mode` from its own client after Litestream starts or restarts and checks the result is 'wal'. Fuss can also check that a -wal file appears next to the database and that data written afterward restores correctly.
  - Workload: 1) sqlite3 db 'PRAGMA journal_mode=DELETE; CREATE TABLE t(id INTEGER PRIMARY KEY);' 2) Start `litestream replicate -config fuss.yml`. 3) Kill -9 at a random delay of 0 to 2s, then restart. 4) Query PRAGMA journal_mode. 5) INSERT rows, stop Litestream, restore, and compare.
  - Guess: Guess: a kill between opening the database and issuing the mode change could leave replication metadata initialized while the database is still in DELETE mode, and a restart might not redo the mode switch.
- **After an abrupt crash, only transactions committed within about the last second (the sync interval) may be missing from the replica; older committed transactions must be restorable.** (process-kill, medium)
  - Quote: > By default, Litestream will replicate new changes to an S3 replica every second. During this time where data has not yet been replicated, a catastrophic crash on your server will result in the loss of data in that time window.
  - Inject: SIGKILL Litestream at random moments during a steady write stream, including mid-sync and right after a large transaction commits.
  - Observe: Fuss logs each committed id with its local commit time. After the kill, it runs `litestream restore -o out.db` and finds the highest contiguous id present. Every transaction committed more than about 1s plus slack before the kill must be present. The restored rows must also form a prefix of the commit order, with no gaps or later rows without earlier ones. `PRAGMA integrity_check` on the restored file must return ok.
  - Workload: 1) Use an S3-compatible endpoint such as a local MinIO, since the 1s default is stated for S3, or set sync-interval explicitly. 2) Start `litestream replicate`. 3) Run INSERT id=n with a timestamp in a loop, about 100/s. 4) Kill -9 after a random 5 to 60s. 5) Restore to a fresh path and compare against the history file.
  - Guess: Guess: if the replica is slow or retries are backing off, the effective window may grow well beyond 1s. A kill during upload could also leave a partial LTX file that restore either chokes on or skips, which would lose more than the window.
- **On a graceful shutdown signal (for example SIGTERM or SIGINT), Litestream flushes every committed change to the replica before it exits.** (restart, high)
  - Quote: > For more typical shutdown scenarios, when Litestream receives a signal to close, it will attempt to synchronize all outstanding WAL changes to the S3 replica before terminating.
  - Inject: Send SIGTERM or SIGINT immediately after a burst of commits, inside the sync interval so the changes cannot yet have been synced by the timer. Repeat this across many restart cycles.
  - Observe: Fuss stops writes, notes the last committed id, sends the signal, and waits for the process to exit. It then restores to a new file. The restored database must contain every id up to and including the last commit made before the signal. Fuss also records the exit code and exit time.
  - Workload: 1) Start `litestream replicate` with a large sync interval such as 10s, so only the shutdown flush can explain the data reaching the replica. 2) Insert N rows in one or more transactions. 3) Immediately send SIGTERM and wait for exit. 4) `litestream restore -o out.db` and check that all N rows are present. 5) Restart Litestream and repeat in a loop.
  - Guess: Guess: the doc says 'attempt'. If the replica errors or the disk is full, Litestream might exit after a timeout without flushing, possibly with exit code 0, so data loss would be silent.
- **Snapshots are taken on the configured interval, old ones are removed after the retention period, and a restore combining the latest snapshot plus later LTX files reproduces all replicated changes.** (restart, medium)
  - Quote: > By default, Litestream takes a full snapshot of each database every `24h` and retains snapshots for `24h`. Between snapshots, changes are stored as incremental LTX files, and a restore replays every LTX file recorded since the most recent snapshot.
  - Inject: Kill or restart Litestream right before, during, and right after a scheduled snapshot, using a short snapshot.interval such as 1m. Also skew the system clock forward and backward across interval and retention boundaries.
  - Observe: Fuss lists snapshot and LTX files in the replica using a read-only directory listing or `litestream ltx`. It records when new snapshots appear and when old ones disappear, and checks these against the interval and retention despite restarts and clock skew. After every cycle it runs restore and checks that the database matches committed history and passes integrity_check.
  - Workload: 1) Config: snapshot: {interval: 1m, retention: 5m}, with a file replica. 2) Start `litestream replicate`. 3) Write rows steadily. 4) Every 30 to 90s, randomly kill -9 or SIGTERM and restart. 5) Occasionally shift the clock by plus or minus 10m. 6) Track replica snapshot files and run restore after each cycle.
  - Guess: Guess: the snapshot schedule may be held in memory and reset on every restart, so frequent restarts could postpone snapshots indefinitely. Clock skew could also make retention delete the only valid snapshot, or keep snapshots forever.
- **The number of snapshots kept in the replica stays at about retention divided by interval.** (clock-skew, medium)
  - Quote: > With a `1h`
interval and `24h` retention you will keep a rolling set of 24 snapshots.
  - Inject: Over a long run with a scaled-down config (interval 1m, retention 5m), jump the wall clock forward or backward, and also restart Litestream.
  - Observe: Fuss counts snapshot files in the replica over time by reading only. The count should hover around retention/interval (about 5) and should never drop to 0 while data exists.
  - Workload: 1) Config: snapshot interval 1m, retention 5m. 2) Run replicate with steady writes for 20 minutes. 3) Inject clock jumps of plus or minus 1h and restarts. 4) Sample the snapshot count every 10s. 5) Run a final restore check.
  - Guess: Guess: retention may compare file timestamps to the wall clock, so a forward jump could delete everything except the newest snapshot, or worse, and a backward jump could stop pruning.
- **If another process checkpoints the WAL behind Litestream's back, Litestream detects it and takes a fresh full snapshot, so the replica stays consistent and restorable.** (concurrent-calls, high)
  - Quote: > However, under high load with many small write transactions (e.g. tens of
thousands per second), the application's SQLite instance can perform a
checkpoint in between Litestream-initiated checkpoints and cause Litestream
to miss a WAL update. When Litestream detects this it takes a fresh full
snapshot to ensure consistency.
  - Inject: Force an outside checkpoint with `PRAGMA wal_checkpoint(TRUNCATE)` from Fuss's client between Litestream syncs. The strongest version: SIGKILL Litestream, write and truncate-checkpoint while it is down, then restart it.
  - Observe: A new snapshot file should appear in the replica after the missed WAL update. A subsequent restore must contain every row committed before the checkpoint and after it, up to the data-loss window, and must pass integrity_check.
  - Workload: 1) Start replicate and insert rows 1..1000. 2) Kill -9 Litestream. 3) Insert rows 1001..2000, then run PRAGMA wal_checkpoint(TRUNCATE). 4) Insert rows 2001..2100. 5) Restart Litestream and wait a few seconds, then SIGTERM it. 6) Restore and check that rows 1..2100 are all present. 7) Also run a live variant with high-rate small inserts and wal_autocheckpoint at its default.
  - Guess: Guess: detection may depend on salt or checksum changes in the WAL header. A TRUNCATE checkpoint followed by a WAL that regrows to a similar size might look unchanged, so rows 1001..2000 could be silently missing from the restore.
- **While Litestream is running, another process cannot complete a full checkpoint because Litestream holds a read lock.** (concurrent-calls, medium)
  - Quote: > Litestream prevents other processes from checkpointing by maintaining a read
lock on the database in between its checkpoint requests.
  - Inject: While Litestream is running and idle between its own checkpoints, and again right after a Litestream restart.
  - Observe: Fuss runs `PRAGMA wal_checkpoint(TRUNCATE)` or `(RESTART)` from its client and records the returned (busy, log, checkpointed) triple. The promise holds if the checkpoint cannot complete (busy=1, or checkpointed < log, or the WAL is not truncated) while Litestream is running, and only completes after Litestream is stopped.
  - Workload: 1) Start replicate. 2) Insert rows so the WAL is non-empty. 3) Wait about 2s. 4) Run PRAGMA wal_checkpoint(TRUNCATE) with busy_timeout set low, log the result, and stat the -wal file size by reading. 5) Kill -9 and restart Litestream, then repeat step 4 at varying delays after restart.
  - Guess: Guess: there may be a gap right after startup, or after a Litestream-initiated checkpoint, before the read lock is re-acquired. An outside checkpoint could slip through in that gap.
- **After `litestream reset`, the next sync produces a fresh full snapshot, and replication then continues correctly.** (process-kill, low)
  - Quote: > If the local Litestream metadata has become inconsistent, run
[`litestream reset`](/reference/reset) on the database to clear the local
tracking state. Litestream will take a fresh full snapshot on the next sync.
  - Inject: Kill -9 Litestream mid-sync, run `litestream reset <db>` while Litestream is stopped, then restart it. A variant kills the restarted process during its first sync, before the fresh snapshot finishes.
  - Observe: A new snapshot file appears in the replica on the first sync after restart. A restore afterward contains all rows committed before the reset and after it, and passes integrity_check. Fuss can also check that the local metadata directory was recreated, by reading only.
  - Workload: 1) Start replicate and insert rows. 2) Kill -9. 3) Run `litestream reset -config fuss.yml /path/db`. 4) Insert more rows. 5) Restart replicate and wait for one sync interval. 6) Read the replica listing for a new snapshot. 7) SIGTERM, then restore and compare all rows.
  - Guess: Guess: if the process is killed during the first post-reset snapshot upload, the replica could hold a partial snapshot plus stale LTX files from the previous lineage, and restore might mix the two.
